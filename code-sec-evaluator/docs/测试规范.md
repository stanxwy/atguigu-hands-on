## 1. 测试总体策略

### 1.1 测试目标

| 目标 | 说明 |
| --- | --- |
| 正确性 | 核心链路（初始化 → 登录 → 创建项目 → 启动任务 → 阶段推进 → 生成漏洞/攻击路径/报告 → 下载报告）在标准输入下行为符合 SPEC §3 与 PRD §10 验收标准 |
| 健壮性 | 非法输入、异常抛出、失败回退均被正确拦截与降级，不产生脏数据、不崩溃 |
| 隔离安全 | 源码只读挂载、命令白名单、容器网络隔离（SPEC Q-5 / PRD R-P0-03）得到验证 |
| 并发一致性 | 多项目并行评估、信号量限流、WebSocket 广播、数据库并发写入保持一致 |
| 可回归 | 新改动不破坏既有功能，覆盖率与门禁在 CI 中强制执行 |

### 1.2 测试范围

- **后端**：`backend/app` 下的 `models`（12 张表映射）、`schemas`（Pydantic 校验）、`api`（15 REST + 1 WS 路由）、`services`（认证/项目/调度/隔离/角色/漏洞/路径/报告/监控/配置）、`core`（JWT/bcrypt/错误码/枚举常量）、`utils`（编号生成、命令白名单、文件）。
- **前端**：`frontend/src` 下的 `pages`（9 页面）、`components`、`hooks`、`store`（Zustand）、`api`（Axios 封装）。
- **集成**：数据库迁移（Alembic）、Docker 隔离环境、WebSocket 实时链路、文件存储（logs/reports/workspace）、报告渲染。

### 1.3 测试优先级（对应 SPEC §5.3 任务分解）

| 优先级 | 覆盖对象 | 触发时机 |
| --- | --- | --- |
| P0 | 认证、项目生命周期、调度阶段机、隔离环境、报告、级联删除（T01–T04） | 每次提交 |
| P1 | 实时监控/WebSocket、系统配置、资源消耗（T05、P1 需求） | 每次提交 |
| P2 | 前端展示层、辅助工具函数 | 每次提交（前端）/ 合并前 |

## 2. 测试分层与工具选型

### 2.1 分层定义

| 层级 | 定义 | 被测对象 | 依赖处理 |
| --- | --- | --- | --- |
| **单元测试（Unit）** | 单个函数/类/模块，无外部 IO | `services/*` 纯逻辑、`core/security.py`、`utils/*`、Pydantic `schemas`、前端 hooks/store/组件 | 全部 mock（DB、docker、LLM、fs） |
| **集成测试（Integration）** | 多模块协作 + 真实外部依赖（可控） | `api` 路由 + service + 真实 SQLite；Alembic 迁移；WebSocket 链路；文件存储 | 用 SQLite（内存/临时文件）替代 MySQL；docker 用真实引擎或 mock |

## 4. 测试命名与组织约定

### 4.1 文件命名

| 后端 | 前端 |
| --- | --- |
| `test_<module>.py`（如 `test_scheduler.py`） | `<Component>.test.tsx` / `<hook>.test.ts` |

### 4.2 测试函数命名

统一采用 `test_<被测行为>_<输入/前置条件>_<期望结果>` 三段式：

```python
# 后端示例
def test_start_project_when_status_completed_should_set_running():
    ...

def test_create_project_with_empty_name_should_return_1001():
    ...
```

```typescript
// 前端示例
it('submits valid credentials and redirects to project list', async () => { ... });
it('shows error toast when password is shorter than 8 chars', async () => { ... });
```

### 4.3 组织约定

1. **Arrange-Act-Assert**：每个用例三段式，禁止在断言前夹带多段业务编排。
2. **一个用例一个行为**：单一断言焦点，避免巨型用例；边界类多用 `@pytest.mark.parametrize` / `it.each`。
3. **用 tag 分组**（回归/冒烟/慢速）：`@pytest.mark.smoke`、`@pytest.mark.slow`、`@pytest.mark.docker`、`@pytest.mark.performance`。
4. **幂等与隔离**：每个用例独立建库/回滚，禁止依赖用例执行顺序（用 `function` 级 fixture）。
5. **聚焦行为而非实现**：断言对外可见结果（HTTP 状态码、响应 JSON、DB 最终状态、推送消息），不断言内部中间变量。

## 5. 六类测试场景

### 5.1 正常流程测试

> 验证核心功能在标准输入下的预期行为，即 PRD §10 验收标准 AC-1 ~ AC-5 的主干路径。

#### 5.1.1 核心链路（端到端业务链）

| 步骤 | 接口/模块 | 测试点 | 期望 |
| --- | --- | --- | --- |
| 1 | `POST /api/system/init` | 首次初始化管理员 | 返回 `code=0` + admin；`users` 表新增 admin，`password_hash` 为 bcrypt（非明文） |
| 2 | `POST /api/system/login` | 正确凭据登录 | 返回 `access_token`（JWT）、`token_type=Bearer`、`expires_in=86400`、`user.role=admin` |
| 3 | `POST /api/projects` | 携带 token 创建项目 | `project_status=created`，字段落库，`created_by` 关联当前用户 |
| 4 | `POST /api/projects/{id}/start` | 启动评估 | 返回 `project_status=running`；异步创建 5 条 `runtime_stages`（`environment_scan/code_analysis/vulnerability_verify/report_generate/done`），初始 `pending`；推送 `project_status` 事件 |
| 5 | Scheduler 阶段推进 | 线性阶段机 | 阶段依次 `pending→running→success`，`started_at/finished_at` 写入，顺序正确 |
| 6 | Worker 角色任务 | 6 类角色 | 每类角色生成独立 `worker_tasks` 记录，`task_status` 流转 `idle→running→success`，`result_summary` 落库，可经 `project_id+stage_id` 回溯 |
| 7 | 漏洞生成 | `vulnerability_service` | `vuln_code` 按 `VULN-0001` 递增，`risk_level` 正确，`verify_status` 流转 `unverified→verifying→verified` |
| 8 | 攻击路径 | `attack_path_service` | `path_code=PATH-0001`，`attack_path_items.step_order` 从 1 递增，`vuln_id` 关联正确 |
| 9 | 报告生成 | `report_service` | `reports` 表 `UNIQUE(project_id)` 满足，`report_markdown` 为权威、`report_html` 由 Python-Markdown 派生，`report_file_path` 指向 `reports/{project_id}/` |
| 10 | 阶段完成 | Scheduler 收尾 | `project_status=completed`，销毁隔离容器，推送 `project_status=completed` |
| 11 | `GET /api/projects/{id}/report` | 查询报告 | 返回 `report_markdown` + `report_html` + `report_id` |
| 12 | `GET /api/projects/{id}/report/download` | 下载报告 | `application/octet-stream`，`Content-Disposition` 含 `report-{project_id}.md`，内容为 Markdown |

```python
# 后端示例（integration/api/test_projects_api.py）
@pytest.mark.smoke
async def test_full_project_lifecycle_flow(async_client, auth_headers, mocker):
    # Arrange
    mocker.patch("app.services.isolation_service.IsolationDriver.create", return_value="container-1")
    mocker.patch("app.services.worker_service.WorkerService.run", side_effect=...)
    # Act
    r = await async_client.post("/api/projects", json={
        "project_name": "示例评估项目", "source_type": "local_path",
        "source_path": "/data/src/demo", "task_content": "评估注入类漏洞",
    }, headers=auth_headers)
    project_id = r.json()["data"]["id"]
    r2 = await async_client.post(f"/api/projects/{project_id}/start", headers=auth_headers)
    # Assert
    assert r.json()["code"] == 0
    assert r.json()["data"]["project_status"] == "created"
    assert r2.json()["data"]["project_status"] == "running"
    # 5 个阶段已创建
    stages = await async_client.get(f"/api/projects/{project_id}/stages", headers=auth_headers)
    names = [s["stage_name"] for s in stages.json()["data"]["list"]]
    assert names == ["environment_scan", "code_analysis", "vulnerability_verify", "report_generate", "done"]
```

### 5.2 边界条件测试

> 覆盖最小值、最大值、空值、超长、特殊字符、枚举非法值，逐字段对齐 SPEC §2 字段约束。

#### 5.2.1 后端边界测试点

| 字段/参数 | 约束来源 | 边界用例 | 期望 |
| --- | --- | --- | --- |
| `project_name` | VARCHAR(128)，必填 1~128 | 空串 / 1 字符 / 128 字符 / 129 字符 / 全空格 / 含 emoji·中文·`<script>` | 空与 129 返回 `1001`；1~128 成功；特殊字符允许（前端转义） |
| `source_path` | VARCHAR(512)，必填 | 空 / 1 字符 / 512 字符 / 513 字符 / 含 `../`·空格·中文路径 | 空与 513 返回 `1001`；合法路径成功 |
| `source_type` | 枚举 `local_path`/`git_repo` | 非法值 `ftp` / 大写 `LOCAL_PATH` / 空 | 返回 `1001` |
| `task_content` | TEXT，可空 | `NULL` / 空串 / 超长（>64KB） | `NULL` 与空串允许；超长按 TEXT 边界验证 |
| `password`（init/login） | 8~64 位 | 7 位 / 8 位 / 64 位 / 65 位 | 7 位与 65 位返回 `1001`；8/64 位成功 |
| `username` | VARCHAR(64)，UNIQUE | 空 / 64 字符 / 65 字符 / 重复用户名 | 空与超长与重复返回 `1001` |
| `page` / `page_size`（列表接口） | int，默认 1 / 10 | `page=0`、`page=-1`、`page_size=0`、`page_size=-5`、`page_size=10000` | 非法值返回 `1001` 或收敛到合法范围；超上限有保护（建议 cap ≤ 200） |
| `risk_level` 过滤 | 枚举 | `critical/high/medium/low` 合法；`xxx`、大小写混用 | 合法过滤生效；非法返回 `1001` |
| `verify_status` 过滤 | 枚举 | `unverified/verifying/verified/failed`；非法值 | 同上 |

## 10. 测试报告与缺陷路由规范

### 10.1 测试报告格式

```markdown
# 测试报告

## Summary
- Total Tests: X | Passed: Y | Failed: Z | Skipped: S
- Coverage: line XX% / branch YY%（后端），statement ZZ%（前端）
- Routing Decision: NoOne / Engineer / Known Issues

## Failed Tests（如有）
- test_xxx: Expected <预期>，Got <实际> — [Source: path/to/file.py]

## Known Issues（第 2 轮仍失败时）
- 问题描述 + 影响模块 + 复现步骤
```

### 10.2 缺陷路由决策

| 判定 | 归属 | 处理 |
| --- | --- | --- |
| 断言符合 PRD/SPEC，实现输出错误 | **工程师（Alex）** | 提交缺陷报告：失败用例、预期 vs 实际、源文件与函数、错误栈 |
| 断言本身写错（与 PRD/SPEC 不符） | **QA（本人）** | 自修测试用例 |
| 全部通过 | **NoOne** | 报告成功，交付 |

### 10.3 测试轮次控制

- **最多 2 轮**：第 1 轮写测→跑测→分析→路由；第 2 轮回归验证。
- 第 2 轮仍失败 → **立即退出**，剩余问题记入「Known Issues」，不再进入第 3 轮。
